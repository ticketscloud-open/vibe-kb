## Каталог `.maestro/`

```text
.maestro/
├── config.yaml   # какие файлы считать тестами при `maestro test .maestro/`
├── auth/         # авторизация (12 флоу)
├── feed/         # лента мероприятий (17)
├── tickets/      # билеты (21)
├── profile/      # профиль, избранное, баланс (18)
├── navigation/   # навигация и бизнес-инварианты (9)
├── onboarding/   # онбординг (5)
├── chats/        # чаты (8)
└── flows/        # переиспользуемые под-флоу для runFlow (8, без префиксов)
```

`appId` всех флоу: `org.ticketscloud.ticketwallet`.

## Именование файлов

Единый стандарт: `<домен>-<сценарий>.yaml`. Префикс сразу указывает на фичу — проще навигация и поиск.

| Префикс | Домен | Примеры |
| --- | --- | --- |
| `auth-` | Авторизация | `auth-login-empty-state.yaml`, `auth-otp.yaml` |
| `onboarding-` | Онбординг | `onboarding-first-launch.yaml` |
| `feed-` | Лента мероприятий | `feed-filters.yaml`, `feed-search.yaml` |
| `tickets-` | Билеты | `tickets-ticket-qr-sheet-opens.yaml` |
| `profile-` | Профиль | `profile-transactions-refill.yaml` |
| `navigation-` | Навигация и инварианты | `navigation-i1-chats-require-ticket.yaml` |

Исключение — `flows/`: под-флоу (`open-login.yaml`, `login-as-user.yaml`, `app-ready.yaml`) префиксов не получают, потому что не являются самостоятельными тестами.

## Правило: 1 TC = 1 flow

Каждый flow закрывает **ровно один** тест-кейс из `docs/test-cases/`. Не собирать assertions нескольких TC в один файл — иначе число flow расходится с числом TC и через несколько месяцев невозможно на глаз понять, покрыт ли конкретный кейс.

Общий *сетап* (логин, онбординг, навигация до экрана) правилом не запрещён: он выносится в `flows/*.yaml` и подключается через `runFlow`. Правило — про *assertions*: если два TC про один экран, у каждого всё равно свой flow, даже если оба на 80% состоят из одного и того же сетапа.

## Изоляция тестов

Flow без `clearState` наследует состояние приложения от прогнанного до него — включая токен авторизации (он в MMKV и переживает `launchApp`). **На это не полагаются**: порядок файлов внутри `config.yaml` не гарантирован, а параллельный прогон (`--shard-all` / `--shard-split`) раскидает флоу по разным эмуляторам. Каждый авторизованный flow логинится сам через `runFlow: flows/login-as-user.yaml` — осознанная цена независимости тестов.

## Теги

Обязательны для каждого теста (минимум один feature-тег), задаются в шапке YAML:

```yaml
appId: org.ticketscloud.ticketwallet
tags:
  - auth        # feature-тег
  - backend     # state-тег (по необходимости)
---
```

- **feature**: `auth`, `feed`, `tickets`, `profile`, `chats`, `onboarding`, `navigation`, `validation` (проверки форм), `invariant` (бизнес-инварианты)
- **state**: `smoke` (быстрый CI-гейт), `backend` (нужна stage-авторизация/backend — не значит «нестабильный»), `stage-seed` (flow готов, но на stage нет нужных данных)

Фильтрация: `--include-tags=smoke`, `--exclude-tags=backend` и т.д. Внутри одного флага список = OR; `--include` вместе с `--exclude` = AND. Как запускать и фильтровать прогон на практике — [[Запуск прогона]].

## config.yaml

Задаёт, что именно запускает `maestro test .maestro/`. Папка = фича: новая домен-папка → добавить glob-строку (`flows/` в конфиг не включать — иначе под-флоу начнут считаться тестами). Backend-зависимые флоу остаются в прогоне и изолируются тегом `backend`; флоу с тегом `stage-seed` — вне конфига до появления сидовых данных.
