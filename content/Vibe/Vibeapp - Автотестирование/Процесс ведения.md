## Матрица трассировки (RTM)

`docs/rtm.md` — таблица «TC → flow → глубина проверки», по строке на каждый из 94 TC+инвариантов. Отвечает на вопрос: *насколько глубоко автотест проверяет сценарий?*

### Глубина (`depth`)

| Значение | Что значит |
| --- | --- |
| `deep` | проверяется поведение и валидация, не только навигация |
| `shallow` | навигация и видимость элементов, без полного бизнес-исхода |
| `shell` | только факт открытия экрана |
| `none` | теста нет |

### Статус (`rtm_status`)

Производное от depth и последнего прогона: `covered` (deep + зелёный прогон) · `partial` (shallow/shell) · `blocked` (упёрлись в backend/фичу) · `missing` · `stale` (раньше проходил, сейчас падает).

## Валидатор целостности

```bash
bun run rtm:check
```

12 автоматических проверок: сводка совпадает с данными, число flow = числу TC, маркеры каталога синхронны с матрицей, нет мёртвых ссылок на переименованные файлы во всей документации, каждый flow матрицы входит в глобы `config.yaml` (иначе Maestro молча его не запустит). Запускается после **любой** правки матрицы или переименования флоу — до зелёного.

## Как добавить новый тест (чеклист)

1. Убедиться, что TC есть в каталоге `docs/test-cases/` (или сначала написать карточку TC).
2. Создать `<домен>-<сценарий>.yaml` в папке домена; шапка: `appId` + минимум один feature-тег (+ `backend`/`smoke` по необходимости).
3. Сетап вынести в `flows/*.yaml`, подключить через `runFlow`. Assertions — только своего TC (правило [[Структура сьюта|1 TC = 1 flow]]).
4. Добавить/обновить строку в `docs/rtm.md`, прогнать `bun run rtm:check` до зелёного.
5. Два живых зелёных прогона нового флоу подряд — только потом коммит.
6. Если элемент без `testID` — запись в `docs/testid-todo.md` с приоритетом; тест до добавления живёт на fallback-селекторе с `TODO`.

## Роли

| Роль | Что получает из процесса |
| --- | --- |
| **QA / автоматизатор** | RTM и [[Карта покрытия приложения]] — что уже покрыто, что дописать |
| **Разработчик** | список защищённых регрессией фич + очередь `testid-todo.md` для приоритизации выдачи testID |
| **PM / руководитель** | зрелость автоматизации по доменам и приоритетам P0–P2 |

## Жизненный цикл статуса

- Прогон упал → в матрице `rtm_status: stale`, разбор причины в `docs/rtm-journal.md`.
- На stage нет данных для сценария → тег `stage-seed`, flow выводится из `config.yaml`, статус `blocked`; после появления сидов — вернуть.
- Поведение изменилось осознанно → сначала обновить TC в каталоге, потом тест.

## Обновление этого раздела базы знаний

Заметки раздела «Vibeapp - Автотестирование» — снимок с ветки `develop` репозитория `vibe-mobile`. Регламент: после мержа значимых изменений (новые домены, изменение сводки RTM, эволюция карты покрытия) — обновить снимок одним коммитом: цифры в обзоре раздела, карту и, если менялись правила, соответствующую заметку.
